# Delivery

Plans, executes, and recovers outbound alert deliveries. Delivery is always live: a destination's own `dry_run` flag is the only way to record a delivery as sent without calling a notifier.

| Import                                 | Function                                                                                                                                                                                                                                                                                           |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@ai-moves/delivery/finalize`          | `planDeliveries` picks enabled, eligible destinations with a document in their language (an `en` destination gets none while `output_lang` is not `en`) and holds each one until quiet hours end (see [Sending](#sending)); `finalizeAlert` stores the alert, documents, and deliveries atomically |
| `@ai-moves/delivery/execute`           | `executeDelivery` applies destination and timing policy, claims a live send, and calls the notifier                                                                                                                                                                                                |
| `@ai-moves/delivery/recovery`          | `recoverExpiredSend` fences an expired `sending` lease to `unknown`                                                                                                                                                                                                                                |
| `@ai-moves/delivery/notifiers/webhook` | `createWebhookNotifier` for Discord and Slack incoming webhooks                                                                                                                                                                                                                                    |
| `@ai-moves/delivery/render/discord`    | `renderDiscord`: one embed per alert                                                                                                                                                                                                                                                               |
| `@ai-moves/delivery/render/slack`      | `renderSlack`: one Block Kit message per alert (see below)                                                                                                                                                                                                                                         |

## Publication

Finalization stores the alert and its language documents atomically, and plans a delivery for each enabled destination that fits when the decision is `send`; the `q-deliver` consumer executes it through the webhook notifier. A `feed_only` decision (a blocking reason such as `below_tier` or `citation_check_failed`) is published on the desk and creates no delivery rows. A destination with `dry_run` set gets dry-run deliveries, which are recorded as sent without calling the notifier and are not paced. The seed SQL printed by `tools/local/seed-sql.ts` sets `profile.output_lang: zh-CN` and a matching Discord destination; it is applied by hand when a database is first initialized, not by the deploy workflow.

## Sending

The push thresholds and delivery policy govern notifications. Publish `delivery.paused: true` to suppress attempted sends with `global_pause` while the desk continues to publish. Suppressions are terminal. The reasons are `global_pause`, `destination_disabled`, `mute`, `source_disabled`, `below_tier`, `update_limit`, and `unverified_content`. `update_limit` applies only to the `update` alerts of forced submissions: with `delivery.max_updates_per_item` (1 by default) already sent for the item, a further one is suppressed. A Hacker News refresh or a changelog notes revision replaces the published alert's documents in place and creates no delivery. `rollout_feed_only`, `quiet_hours`, and `rate_limit` remain in the enum only for historical rows: nothing writes them any more. The rollout switch is gone, and quiet hours and the send interval now delay a delivery instead of dropping it.

- **Quiet hours defer.** `planDeliveries` takes the end of the window that `now` falls in, for `delivery.quiet_hours` and the destination's own `quiet_hours` (the later one when both apply, following a chain where one window's end lies inside the other; windows may cross midnight and are read in their own time zone). The delivery is planned with `next_attempt_at` at that instant and `expires_at` = that instant + `delivery.expiry_hours[kind]`, so the lifetime counts from when sending may start: an HN story found at 02:00 JST under the default 23:00–07:00 window is sent from 07:00 and expires at 13:00. Outside quiet hours both fields are as before (`next_attempt_at` null, `expires_at` = now + expiry). The `deliver` job queued at finalize returns early while `next_attempt_at` is in the future. The sweep, which runs on the 5-minute tick, queues every pending or `failed_retryable` delivery whose `next_attempt_at` has passed (`listDue`, oldest `next_attempt_at` then id first), so sending starts at the first tick on or after the window end: up to 5 minutes later, plus queue delay.
- **A due attempt inside quiet hours** (a retry whose backoff ended after 23:00, or a configuration change) is not suppressed: `executeDelivery` keeps the row in its state (`pending -> pending` or `failed_retryable -> failed_retryable`), sets `next_attempt_at` to the window end, and moves `expires_at` later by the same wait. Deterministic suppressions (pause, disabled destination, source, tier) are decided before quiet hours and apply at once. The update limit depends on what was already sent, so `claimForSend` settles it with the claim.
- **Pacing.** With `delivery.min_interval_minutes` above 0, `claimForSend` allows a live send only when no other alert's live delivery is `sending` and none became `sent` or `unknown` within that interval. A delivery that comes too soon is not dropped: it stays `pending` or `failed_retryable` with `next_attempt_at = now + min_interval_minutes` and `expires_at` moved later by the same interval, no attempt is counted, nothing is reserved, and `executeDelivery` ends the run (`deferred`). The sweep picks it up again once due, so a backlog drains at most one delivery per interval and, because the sweep ticks every 5 minutes, effectively one per tick when the interval is 5 minutes or less. `0` turns pacing off. Dry-run deliveries are not paced. Every deferral extends `expires_at`, so a message that quiet hours or pacing delayed does not expire for waiting; `update_limit`, `expired`, and the other terminal outcomes are unchanged.
- The webhook URL is a secret named by the destination's `secret_ref`, and must be HTTPS on `discord.com` or `hooks.slack.com`. Each call makes one request with `redirect: "manual"`. Discord adds `wait=true`, and a 2xx counts as sent only when its receipt is at most 64 KiB of JSON carrying a message `id`; Slack discards the body of any 2xx and records no message ID.
- A 5xx is an answer that the message was not taken: `UPSTREAM_UNAVAILABLE`, retryable. A 429 is `UPSTREAM_RATE_LIMITED`, retryable. Any other non-success, including a redirect, is `UPSTREAM_REJECTED`, permanent.
- No response, a Discord receipt that is oversized or lacks an `id`, or no answer within `timeouts.notifier_ms` (default 10 s, applied in `executeDelivery`) is `OUTCOME_UNKNOWN`: the delivery becomes `unknown` and is never resent, because the message may have arrived.
- Retryable failures move to `failed_retryable` and back off per `retry.deliver` (5 attempts by default); the last one becomes `failed_permanent` with `ATTEMPTS_EXHAUSTED`.

## Discord cards

A Discord delivery requires a `send` decision with no blocking reason and a stored document that belongs to the alert, matches the destination's language without an English fallback, and passes the public-link rules; otherwise the delivery is suppressed before any claim or secret lookup. The card has a title linking to the desk article, the summary, key points grouped by category (breaking, new, change, fix) with their implications as subtext, and the source link as the last field. Points that carry an evidence quote are left out, markup and mentions are escaped, and every length is bounded to Discord's embed limits.

A submission card has its own violet accent, no product mark, and a footer naming the submitter (`submittedByLabel`) in place of the repeated source label. Before a Discord send, the document's `submitted_by` must equal the display name recorded on the item's `score_json`; the email never reaches a card.

Discord selects [locale pack](../locales/README.md) labels from the document language. `node tools/local/card-json.ts` prints a card for a stored document without sending it.

## Slack

`renderSlack` returns `{ text, blocks }` for an incoming webhook, under the same suppression rules as a Discord card. Labels come from the same [locale pack](../locales/README.md) entries as Discord (`groupLabels`, `pointsLabel`, `readingLabel`) plus the button labels.

| Block                   | Content                                                                                                                                                                                                                                                                             |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `header`                | The title as `plain_text`, code marks removed, clipped to 150 characters with an ellipsis                                                                                                                                                                                           |
| `context`               | A kind mark (📦 release, 🔥 discussion, 📮 submission), the source label, and for a submission `Submitted by: <name>` (the `submittedByLabel` copy), as `plain_text`                                                                                                                |
| `rich_text`             | The summary, unless it repeats the title                                                                                                                                                                                                                                            |
| `divider`               | Before and after the points, when there are points                                                                                                                                                                                                                                  |
| `section` + `rich_text` | Per point group (breaking, new, change, fix), or one points list for a discussion: the bold label as an escaped `mrkdwn` section, whose padding separates the groups, over a bullet list; each reading is a quote right under its point, opening with 💡 and the bold reading label |
| `actions`               | Link buttons with emoji: the desk article (primary), the source, and the Hacker News discussion when there is one                                                                                                                                                                   |

- The top-level `text` is a short fallback for notifications: the source label and the title, escaped, unlinked, and without code marks.
- Only locale copy (group labels) is written as `mrkdwn`; model text goes into `rich_text` blocks, which Slack never parses: `@here`, `<!channel>`, `*`, and stray backticks stay literal, and nothing needs escaping. A balanced backtick pair becomes a piece styled as code, so inline code renders the same next to Japanese or Chinese text as next to spaces, and copies without hidden characters. Addresses in model text are broken so Slack does not link them; every link is a button URL that passed the public-link rules.
- Points that carry an evidence quote are left out, so neither a quote nor a comment ID ever reaches Slack.
- Lengths stay within Block Kit limits: 150 characters per header, 3,000 per rich text block and context element, 75 per button label, 3,000 per URL. The layout has at most sixteen blocks, under the limit of 50.
- An invalid desk link or an empty title throws `CONTENT_UNSUPPORTED`, as for Discord.
